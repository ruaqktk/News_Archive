# 뉴스 브리핑과 아카이빙 운영 지침

## 활성 예약

- 이름: 단독·기획 아침 브리핑
- 실행: 매일 오전 9시, Asia/Seoul
- 기간: 전날 오전 9시 이상, 당일 오전 9시 미만의 최초 발행 기사
- 실행 범위: ChatGPT 한국어 브리핑, 날짜별 JSON 파일 보존, GitHub 기사 데이터 누적
- GitHub: 연결 계정 `ruaqktk`, 저장소 `ruaqktk/News_Archive`, 브랜치 `main`
- 웹사이트 반영: Vercel 최초 배포는 미완료. 같은 저장소를 연결한 뒤 해당 커밋의 배포 성공을 확인

오전 9시는 작업 시작 시각입니다. 결과 전달은 원문 확인과 요약이 완료된 뒤 이뤄집니다.

연결 계정 `ruaqktk`으로 `News_Archive`에 실제 파일 쓰기가 성공한 것을 확인했습니다. GitHub에 데이터를 누적하는 작업은 Vercel 최초 배포와 독립적으로 수행합니다. Vercel이 아직 연결되지 않았거나 배포 상태를 확인하지 못한 경우 웹사이트 반영 완료로 보고하지 않습니다.

## 분류와 요약

1. 단독: 해당 기사 제목이나 기사 자체에 명시된 단독 표기. 단독주택, 단독주연, 단독판사 등 일반 용례는 제외합니다.
2. 기획: 해당 기사 자체의 기획 표기나 공식 기획·연재 소속이 확인돼야 합니다. 메뉴/관련기사의 '기획'이라는 단어는 근거가 아닙니다.
3. 최초 발행시각과 수정시각을 구분합니다. 기사 주소에 들어 있는 날짜를 발행시각으로 추정하지 않습니다.
4. 기사당 확인한 사실을 2~3문장으로 자체 요약하고 원문 URL을 제공합니다. 본문을 읽지 못한 경우 확인 범위를 표시합니다.
5. 제목·URL·발행시각·본문·분류 근거의 일치를 확인합니다.
6. 기사 없음, 부분 확인, 접근 제한, 수집 실패를 구분합니다.
7. 동일 매체의 유료판/지면판 등 사실상 같은 기사도 내용과 URL을 비교해 중복을 점검합니다. 다른 매체가 독립 취재한 기사는 각각 유지합니다.

## 데이터 계약

웹사이트는 `public/data/archive.json` 하나를 읽습니다.

```json
{
  "schemaVersion": 1,
  "timezone": "Asia/Seoul",
  "updatedAt": null,
  "publishers": [],
  "runs": []
}
```

위 형태는 구조 설명용입니다. 실제 파일에는 지정한 9개 publisher 객체가 반드시 있어야 합니다. 각 객체는 `id`, `name`, `domain`, `url`을 가집니다.

일일 JSON은 아래 필드를 가진 run 객체 한 개입니다.

| 필드 | 내용 |
|---|---|
| date | 브리핑 날짜, YYYY-MM-DD |
| generatedAt | 결과 생성 시각, 초와 시간대 포함 ISO 8601 |
| windowStart / windowEnd | 수집 대상 최초 발행시각 구간 |
| status | complete / partial / failed |
| note | 실행 범위와 제한 설명 |
| coverage | 9개 언론사의 상태와 기사 수 |
| articles | 검증한 기사 배열 |

coverage 객체: `publisherId`, `status`(checked/partial/blocked/not_checked), `note`, `articleCount`.

article 객체: `id`, `publisherId`, `type`(exclusive/feature), `title`, `url`, `publishedAt`, `collectedAt`, `summary`, `summaryBasis`(full_text/partial_text/metadata_only), `classificationEvidence`.

`publishedAt`은 확인할 수 없으면 null이지만, 기간에 들어온다는 증거까지 없으면 기사 목록에 넣지 않고 수집 제한으로 보고합니다. complete는 9개 언론사 모두 정해진 조사 범위를 확인했을 때만 사용합니다.

## GitHub 자동 저장 실행 절차

1. 대상 저장소와 `main`의 현재 데이터 및 파일 SHA를 읽습니다. 권한이 없거나 파일 읽기에 실패하면 기존 데이터를 빈 배열로 간주하지 않습니다.
2. 새 run을 구성하고 기존 데이터와 병합합니다. 로컬 코드 실행이 가능하면 `scripts/merge-run.mjs`를 사용합니다.
3. 기존 날짜·기사 보존, 동일 URL 중복 제거, 9개 coverage 수치, 공식 도메인, 날짜를 검증합니다.
4. 바뀐 `public/data/archive.json`만 현재 SHA를 조건으로 갱신합니다. 충돌 시 최신 파일을 다시 읽어 병합하고, 다른 변경을 강제로 덮어쓰지 않습니다.
5. 반환된 커밋을 확인합니다. GitHub 저장 성공 후 가능한 경우 Vercel의 배포 상태를 확인합니다. 배포를 확인하지 못했으면 '데이터 저장 완료 / 사이트 반영 확인 중'으로 구분합니다.
6. 저장 실패 시 원래 브리핑과 일일 JSON은 제공하고 실패를 표시합니다. 실패한 상태를 웹사이트 업데이트 완료로 보고하지 않습니다.

예약의 범위나 실행 지침을 변경할 때는 새 예약을 추가하지 않고 기존 **단독·기획 아침 브리핑** 예약을 수정해 중복 실행을 막습니다. 연결 계정이나 저장소를 바꾸면 접근 권한과 실제 쓰기를 다시 확인합니다. Vercel 최초 배포가 아직 완료되지 않았어도 GitHub 데이터 누적은 독립적으로 수행할 수 있습니다.

## 최초 샘플과 반복 실행

2026-10-26의 초기 샘플은 정기 브리핑과 조사 구간이 다릅니다. 같은 날짜의 첫 정기 결과와 병합하면 기존 5건을 보존하고 조사 구간을 합치므로, 넓어진 전체 구간을 모두 조사하지 않았다면 상태는 `partial`로 유지합니다. 해당 날짜의 note에는 초기 샘플을 보존했으며 정기 조사 범위는 전날 09시부터 당일 09시까지라는 설명을 넣습니다.

브리핑 기사 수, 새로 추가한 기사 수, 해당 날짜의 누적 기사 수를 구분합니다. 재실행이 실패해도 기존 기사를 보존하며, 최신 시도 시각만으로 최근 수집이 성공했다고 표현하지 않습니다. `status`와 `coverage`를 함께 확인합니다.
